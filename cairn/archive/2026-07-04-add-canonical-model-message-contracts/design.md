# Design: Add canonical model message contracts

## Context

The current model adapter boundary is intentionally small and stable, but provider compatibility now needs more structure than a single prompt string can carry. Existing accepted contracts already cover model dispatch planning, image descriptors, token/thought streaming, provider registry metadata, and future provider parity criteria. This change connects those rails through a canonical request/response shape while keeping concrete provider serialization in host adapters.

## Decisions

### 1. Add a parallel versioned contract before replacing compatibility DTOs

**Choice:** Introduce canonical message request and response envelope DTOs with new contract identities while leaving the simple prompt/message DTOs available as compatibility helpers.

**Rationale:** Embedders can migrate gradually, and existing tests keep proving the old path does not gain authority.

### 2. Keep request structure provider-neutral

**Choice:** Represent ordered model messages, role labels, content parts, tool declarations, response-format intent, sampling/output controls, reasoning/thinking requests, and safe metadata without provider-native wire fields.

**Rationale:** A single canonical shape lets provider adapters perform explicit, testable projection instead of receiving ad hoc prompt strings or raw provider payloads.

### 3. Keep response semantics explicit

**Choice:** Model responses should report assistant text, structured payloads, tool-call requests, refusal/safety status, usage, and finish reason as typed variants or fields.

**Rationale:** Provider compatibility depends on knowing whether the response is final text, a tool call, a safety refusal, malformed output, or a structured payload without scraping provider-specific JSON.

### 4. Legacy bridge is pure and authority-neutral

**Choice:** The existing `ModelRequest { prompt }` path projects to a canonical user-message request with compatibility defaults, and canonical assistant-text responses project back to `ModelResponse { message }` only when no structured/tool/refusal semantics would be lost.

**Rationale:** Compatibility should preserve behavior, not hide new semantics or silently downgrade provider output.

## Risks / Trade-offs

- More DTO structure can increase validation complexity. Keep the functional core pure and use small validators with explicit bounds.
- Provider projection can drift if expected payloads are generated by the same builder. A follow-up conformance change adds literal provider fixtures.
- Compatibility projection can become lossy. Fail closed when canonical responses carry non-text semantics that cannot be represented by the old message DTO.
