# Design: Add provider projection conformance fixtures

## Context

The accepted provider parity note says provider-native message conversion fixtures become mandatory when provider-specific request DTOs exist. The canonical request and capability matrix changes make that activation point concrete: any adapter that claims support for a provider family must prove canonical semantics survive provider-native projection and response normalization.

## Decisions

### 1. Fixture harness is provider-family scoped

**Choice:** Define conformance cases per provider family and API style, such as OpenAI Responses, OpenAI-compatible chat/local HTTP, Anthropic Messages, mock, and any future claimed family.

**Rationale:** Compatibility behavior differs by provider family. A single generic JSON fixture would hide important wire-shape differences.

### 2. Expected payloads are literal fixtures

**Choice:** Expected provider-native requests and canonical responses must be literal reviewed fixture data, not generated by the same projection builder under test.

**Rationale:** This catches dropped roles, tool declarations, structured-output intent, image descriptors, stream options, reasoning controls, and metadata drift.

### 3. Response normalization is part of conformance

**Choice:** Provider-native responses must normalize into the canonical response envelope with typed assistant text, structured payloads, tool calls, refusal status, usage, finish reasons, and typed malformed-output failures.

**Rationale:** Compatibility failures happen as often on output as on input, especially for tool calls, refusals, and finish/usage semantics.

### 4. Streaming claims require parser-entrypoint evidence

**Choice:** Any provider family that claims streaming support must feed raw stream bytes or chunks through the production parser entrypoint and compare canonical frames.

**Rationale:** Helper-only parser tests can pass while production chunk handling, terminal ordering, usage records, or tool-call deltas drift.

### 5. Conformance index records not-applicable reasons

**Choice:** Maintain a conformance index that records supported, unsupported, and not-applicable cases with reasons for each provider family and feature class.

**Rationale:** Reviewers can distinguish intentional unsupported features from missing coverage.

## Risks / Trade-offs

- Literal fixtures require maintenance when provider APIs evolve. Keep fixtures focused on stable compatibility semantics instead of full provider payload dumps.
- Provider-native data can include sensitive payload shapes. Fixtures must use synthetic values and safe leak sentinels only.
- Some local gateways emulate OpenAI partially. Mark unsupported or not-applicable features explicitly instead of pretending full parity.
